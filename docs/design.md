# 设计取舍

这份文档记录「为什么这么写」，方便评审快速判断工程含量，也方便后来者改。

## 1. 为什么选「适量点餐」而不是「更省钱」

赛前观察了官方榜单（活动期间公开）：前 100 个项目里，省钱类（`*-saver`、`*-budget-*`）、热量/减脂类（`*-calorie-*`、`*-fit-*`）、娱乐类（塔罗、抽卡、MBTI）几乎覆盖了所有常见方向，拼单/分账也有人做了。

剩下的真空是**「这桌人到底吃得下多少」**：预算没超、菜剩一半，是更普遍也更难被算法解决的浪费。它有三个好处：

- 官方规则明确反对「宣扬不健康饮食方式、奢靡浪费」，立意与主办方一致；
- 份量是可计算的（能量区间 + 组合搜索），不依赖大模型瞎猜，工程质量可被检验；
- 输出天然有画面感：一桌菜 vs 该点多少，演示成本低。

代价是它不会「劝你多买」，从纯商业角度不是最优卖点。这里选择站在用户和反浪费一侧。

## 2. 份量模型：为什么是区间，不是数字

单点目标（比如「每人 720 kcal」）会让输出显得精确，但输入本身很模糊：同一个人今天饿不饿，谁也不知道。用区间有三个好处：

- 承认不确定性，避免「差 5 kcal 判你点少了」这种荒谬结论（实现里还额外给了 2% 的 verdict 容差）；
- 给求解器留出「更便宜但仍在区间内」的空间；
- 输出「目标 2592–3168 kcal，方案 2620 kcal」比「推荐 2620 kcal」更容易被复核。

人群/食量系数取整数值而非拟合曲线，是因为没有真实标注数据；与其假装精确，不如把假设写在明面上。营养数值同理：`fixtures/README.md` 与 README 都明确写了「量级参考，不构成营养建议」。

## 3. 罚分为什么不对称（1.2 vs 0.8）

```
kcal > hi  →  1.2 * (kcal - hi) / hi      # 剩食
kcal < lo  →  0.8 * (lo - kcal) / lo      # 不够吃
区间内      →  0.05 * |kcal - mid| / mid   # 靠近中心
```

「不够吃」可以再补一份，「点多了」只能扔。所以剩余罚分高于不足罚分。这个系数是最容易按场景调的旋钮，放在 `portion.waste_penalty` 一处。

## 4. 两阶段求解：把网络调用压到个位数

朴素做法是对每个候选组合调 `calculate-price`。4 人、7 主食、7 配菜、7 饮料的最坏情况是 `7×8×8 = 448` 个组合/组；多组叠加直接破千次调用，撞上官方 600 次/分钟的限流。

因此拆成：

1. **营养阶段**（0 次网络）：本地枚举、按罚分排序，每组只保留 top-k（默认 6）；
2. **核价阶段**（≤ `price_top` 次）：只对总排名前 6 的方案核价，再叠加价格项排序。

单元测试 `test_price_calls_are_bounded` 把「一次 plan ≤ 4 次核价调用」钉死，防止后人改出限流事故。

复杂度：单组 `O(|M| × |S| × |D|)`，组合阶段 `O(k^g)`（k=6, g=组数）。g=3 时最多 216 个组合，纯 Python 毫秒级。

## 5. 配菜共享：`ceil(n/2)` 的依据

薯条、鸡块、鸡翅这类 `shared` 餐品按两人一份下单。这是一个保守的经验值：

- 一人一包薯条在 4 人以上的桌子里几乎必然剩；
- 两人一份又不会让谁吃不到——而且不够可以加，剩了只能扔。

`shared` 由名称关键词判定（薯条/鸡块/鸡翅/玉米/沙拉…），也可在数据源里显式标注。

## 6. MCP 客户端为什么自己写，且 schema 驱动

- **自己写**：官方文档只给了接入地址和协议，没有提供 Python SDK；用标准库实现约 260 行，换来「零依赖、`git clone` 就能跑」，对评审更友好。
- **schema 驱动**：字段名随服务端演进而变的概率不低。写死 `storeCode` 一旦被改成 `storeId`，项目会静默传错参数。改为读 `inputSchema` + 语义别名映射后，失败会带着「缺哪个字段、怎么查」的信息抛出来。
- **SSE 兼容**：Streamable HTTP 可能返回 `text/event-stream`，也可能返回纯 JSON；两种都解析，避免在某些网关下直接崩。

## 7. 明确不做的事

| 不做 | 原因 |
|---|---|
| 下单 / 支付（`create-order`） | 让 Agent 替人花钱的风险 > 便利收益；本项目定位是「算清楚」，不是「自动买」 |
| 登录态 / 账号信息读取 | 只需要一个 MCP Token，不碰任何用户凭证 |
| 用大模型生成营养数据 | 营养必须来自 `list-nutrition-foods`，否则整条推理链不可信 |
| 猜真实价格 | 拿不到 `calculate-price` 就标注 `estimate`，不假装是实价 |

## 8. 可以怎么继续做

1. **残食反馈闭环**：饭后记录「剩了几份」，把系数按门店/人群在线学习，让模型越用越准；
2. **多人不同套餐**：目前同组同配置的人吃同一套，未来支持「每人各点一份但总量最优」；
3. **时间维度**：结合 `campaign-calendar` 与券到期时间，回答「今天点还是明天点」；
4. **可视化**：把终端报表换成一张可分享的账单图，降低传播成本。
